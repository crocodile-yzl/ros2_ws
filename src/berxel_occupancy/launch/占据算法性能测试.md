# 占据算法性能实测与 NUC 粗略估计

当前电脑：Intel Core i7-14650HX。相机：博升 P100R，640×400 深度图，实际输入约30.3fps。深度上限3m，像素采样步长4，相机高0.9m、下俯34°，RViz关闭。复用正在运行的相机驱动，每次仅运行一个占据节点。

## 实测

CPU百分比中，100%表示占满一个逻辑核，不是整机百分比。RSS为占据节点采样峰值，不含相机驱动。

|体素|定时器频率|实际地图更新率|占据节点CPU|节点RSS|
|---|---:|---:|---:|---:|
|10cm|20Hz|20.00Hz|15.5%|25.5MiB|
|10cm|30Hz|28.24Hz|19.5%|25.7MiB|
|5cm|20Hz|20.00Hz|38.4%|27.1MiB|
|5cm|30Hz|28.09Hz|52.7%|26.6MiB|
|10cm|60Hz|30.28Hz|22.0%|25.3MiB|
|5cm|60Hz|30.04Hz|56.4%|27.4MiB|

四组主测试各预热5秒、采样约20秒；两组补测各预热3秒、采样约12秒。相机驱动CPU约8.5–12%，RSS约88MiB。场景为测试时的实时画面，各组依次执行，不保证场景完全相同。

提高定时器到60Hz后，10cm达到30.28Hz，5cm达到30.04Hz。60Hz仅表示检查新图像的频率，每张图像最多处理一次，实际输出受约30fps相机输入限制。结果支持原30Hz设置的约28Hz主要受定时器与图像到达时序影响，不能据此判断算力不足。输出仍有抖动，平均30Hz不等于每帧都在33.3ms内完成。

5cm接近30Hz时，占据节点加相机驱动合计约0.65个逻辑核的CPU时间，内存约115MiB。占据节点平均每次更新消耗约18.8ms进程CPU时间；这不是端到端延迟。

## ASUS NUC 15 Pro / Core Ultra 7 255H 估计

尚未在NUC实测，以下是基于当前测量的粗略判断；不能按核心数量、功耗或AI TOPS线性换算。当前算法使用CPU，未调用Arc GPU或NPU。

|配置|NUC运行判断|
|---|---|
|10cm、20Hz|较有把握，余量充足|
|10cm、约30Hz|预计可行，需使用避免漏帧的调度设置|
|5cm、20Hz|推荐首先尝试，预计可行|
|5cm、约30Hz|有希望达到，需在NUC确认持续帧率和抖动|

作为假设情景，如果NUC每帧CPU工作耗时是当前电脑的1.5倍，则5cm约28ms，对33.3ms帧周期仍有一定余量；如果达到2倍，则约38ms，30Hz将吃紧而20Hz更合适。这些倍数是容错情景，不是测得的NUC性能差异。

测试未覆盖长期热稳态、其他机器人任务并发、不同障碍物场景或RViz开销。最终应在NUC上连续运行并检查频率、最慢帧及温度。此次未修改默认配置，仍为3m、10cm、20Hz。测试结束执行了恢复原节点的操作，但最终检查时原相机和占据进程均已退出，退出原因未确认。
